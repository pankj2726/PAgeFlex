## TASKS-02 additions

| ID | Area | Cause / what is not handled | Workaround / status |
| --- | --- | --- | --- |
| KL-T2-GATES | **All three task gates** | **ENV**: no browsers, Playwright, Adobe Reader/Preview, pixel-diff harness or deploy. Nothing in the three "Gate" lists was executed, so **no gate has passed**. Unit tests and 4 Playwright specs are written; none has run. | Run the commands at the top of `tests/e2e/*.spec.ts` and `npx vitest run`. |
| KL-GLYPH | Glyph geometry (Task 2) | pdf.js 5.x as bundled exposes no per-glyph advances. Each item's width is spread over its characters with a proportional-width table (`charWeight`). Item and word extents are exact; letter boundaries inside a word may be off by a fraction of a glyph, so a drag that ends mid-word can land one character away and a cover may be a hair too wide/narrow at its ends. | Handles (⇤± / ±⇥) fix a range by one character. |
| KL-EDIT-2 | **Real removal / OCR layer not done** (Task 2.3) | Content-stream surgery (removing only the target glyphs from the page's Tj/TJ operators, across simple and CID fonts) is **not implemented**. Edits are cover-and-replace: the original words stay in the file's text layer under the cover, and an OCR layer's invisible words are **not** updated, so search/extraction can still find the OLD text as well as the new. The export dialog reports "original words are covered, not deleted" per page, and the post-edit check tolerates exactly that (and nothing else). | Use Redact to remove text permanently. |
| KL-EDIT-3 | Multi-line targets | A target spanning lines gets one cover rectangle per line but ONE replacement text object drawn from the first line's baseline with 1.2× leading; it will not reproduce the original line pitch or wrapping. | Edit one line at a time. |
| KL-EDIT-4 | Appearance matching | Family (sans/serif/mono), bold/italic, size, colour and baseline are matched; letter-spacing, word-spacing, horizontal scaling and the actual embedded font are not (text is written in a standard-14 font). Colours are sampled from the pixels around the first target glyph only. | – |
| KL-T2-ROT | Rotated/skewed runs | Items with a rotation > ~3° are hit-testable but refused for editing ("use Whiteout + Text box"). | – |
| KL-COLUMN | Layout heuristics | Columns/lines are inferred: a horizontal gap > 1.6 em splits a line (gutter / table cell); a segment wider than 60% of the text width separates bands; a new column starts when a line overlaps the previous line (reading order) by < 30%. Table cells separated by less than 1.6 em, text over shapes, and unusual flows can still be grouped wrongly (words are always split correctly, so single-word edits are unaffected). | Debug overlay `?debug=text` shows the grouping. |
| KL-EDITVERIFY | Post-edit verification | The output check compares multisets of non-whitespace characters (robust to spacing differences between PDF producers, blind to same-letter reordering). It is skipped on pages containing redactions (those are rasterised). On failure the affected pages' edits are rolled back by re-exporting without them; the export is slower (second parse). | – |
| KL-FR-1 | Replace All threading | Matching of literal queries and the replace planning run cooperatively on the main thread (pdf.js parses in its own worker; regex mode runs in a terminated-on-timeout worker). It reports progress and can be cancelled between pages, but it is not in a dedicated worker, so a very large replace can make the UI feel sluggish. | – |
| KL-FR-2 | What is searched | Glyphs hidden under earlier cover rectangles are excluded (so replaced text is not found again); text typed into Text boxes / edit objects is **not** searched. Hyphenation joining is heuristic (D-FR-4). No `$1` capture groups in replacements (always literal). Case-aware replace handles "Title" and "ALLCAPS" only; no Turkish dotless-i rules. | – |
| KL-T2-FIXTURES | Fixtures | The Task 2 fixture list (dense paragraph, two-column, tables, super/subscript, overlapping text, rotated + CropBox pages, scan with OCR, justified/ligatures, Devanagari, earlier edits) is covered only by SYNTHETIC layouts in `src/tests/glyphMap.test.ts`. The real PDFs still have to be added (`tests/fixtures/README.md`). The pixel-diff, OCR-search and "neighbour pixels unchanged" checks exist only as e2e code that has not run. | – |
| KL-T1-REPRO | Task 1 reproduction | The failure was **not reproduced in a browser**. Root cause was identified from the pdf-lib fork's source (see DECISIONS D14); the other hypotheses were audited and either fixed as hardening or ruled out by reading the code. A download failure from another cause would not be fixed by this work. | The new dialog shows the exact error and a fallback link. |
| KL-A11Y | Accessibility | The page canvas is inherently not screen-reader readable; toolbar/dialogs have ARIA labels and keyboard operation. No axe run was possible. | – |
| KL-LH | Lighthouse targets | Not measurable here (ENV). The single-file bundle includes pdf.js + pdf-lib inline, so the 200 KB gzipped initial-JS budget (Section 10) is **very likely exceeded**; `scripts/bundle-budget.mjs` reports actual size. | Dynamic import does not code-split with `vite-plugin-singlefile`. |
| KL-N | Non-goals | N1–N4 (Office conversion, PKI signatures, reflow, accounts) are out of scope and disclosed in the UI. | – |
